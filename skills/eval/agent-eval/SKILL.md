# 에이전트 평가

사용자 입력: $ARGUMENTS

대상 에이전트는 `.claude/agents/*`에서 확인한다. 평가 케이스는 병렬로 실행하고,
설정 간 비교와 같은 케이스의 반복 실행은 순차적으로 진행한다.

시작 전에 채점 기준과 케이스 형식을 읽는다. 경로는 이 스킬 디렉터리를 기준으로 한다.

- 채점 기준과 판정: `rubrics/agent-run-quality.md`
- 케이스 형식과 실행 방법: `cases/README.md`

실행·집계 도구는 `scripts/`에 있으며 아래 단계의 명령으로 사용한다.

## 0. 평가 범위와 비용 확인

사용자 입력과 저장소에서 확인할 수 있는 값을 먼저 사용한다. 빠진 항목에는 다음 기본값을 적용한다.

| 항목 | 기본값 |
|---|---|
| 대상 에이전트 | 작성·감사 역할. 탐색 전용 에이전트는 현재 루브릭의 일부 검증 항목이 적용되지 않음 |
| 비교 설정 | `.claude/`에 미커밋 변경이 있으면 BEFORE·AFTER 비교, 없으면 단일 측정 |
| 반복 횟수 `k` | 3 |
| 케이스 | 기존 `~/.claude/evals/cases/<repo>/`를 재사용하고 부족한 유형만 추가 |

`케이스 수 × 설정 수 × k`로 전체 실행 횟수를 계산하고, 이전 실행 기록이 있으면 시간과 비용을
추정한다. 기록이 없으면 추정의 불확실성을 알린다. 예상 비용을 제시하고 진행 여부를 확인한다.
사용자 확인 없이 총 6회를 초과해 실행하지 않는다.

## 1. 평가 케이스 준비

최소 구성은 T1·T2·T3 결함이 포함된 케이스와 정상 대조군(negative control) 1개다.
기존 케이스를 확인하고 부족한 난이도별로 `Agent(subagent_type="eval-case-author")`를 하나씩
병렬 실행한다. 대조군이 없으면 결함 없는 케이스도 준비한다.

각 에이전트에 다음을 전달한다.

- 대상 에이전트와 역할(작성·감사)
- 담당 난이도와 결함 수: T1 결함 하나와 필요한 T2·T3 결함 2~3개
- 저장소 경로와 기준 커밋(`git rev-parse HEAD`)
- 케이스 ID 형식: `<agent>-<주제>-<tier>`
- 임시 워크트리에서 검증 게이트를 실행해 정답을 확인하고, 원본 작업 트리는 변경하지 않을 것

반환된 케이스 디렉터리와 실제 게이트 결과를 확인한다. `git apply --check`로 패치를 적용할 수
있는지 검증한다. 케이스 구조와 결함 분류는 `cases/README.md`를 따른다.

## 2. 실행

```bash
${CLAUDE_PLUGIN_ROOT}/skills/eval/agent-eval/scripts/run-suite.sh ~/.claude/evals/cases/<repo> --label BEFORE --k 3 --jobs 3
${CLAUDE_PLUGIN_ROOT}/skills/eval/agent-eval/scripts/run-suite.sh ~/.claude/evals/cases/<repo> --label AFTER --k 3 --jobs 3 \
  --harness <저장소>/.claude
```

- `--jobs`는 동시에 실행할 케이스 수이며 기본값은 3이다. 같은 케이스의 `k`회 실행은
  워크트리를 공유하므로 순차적으로 진행해 회차 간 메모리를 복원한다.
- BEFORE가 종료된 뒤 AFTER를 실행한다. 두 설정을 동시에 실행하면 시스템 부하가 소요 시간 비교에 영향을 준다.
- BEFORE는 케이스의 기준 커밋에 저장된 하네스를 사용한다. AFTER의 `--harness`는 지정한
  `.claude/`와 인접한 `CLAUDE.md`를 적용한다. 기준 커밋이 HEAD보다 오래됐다는 경고가 나오면
  비교하려는 버전이 맞는지 확인하고 필요하면 케이스를 갱신한다.
- 스위트가 종료 코드 1을 반환하면 실패한 케이스를 확인한다. 설정 간 케이스 수가 다른 상태로 집계하지 않는다.
- 장시간 실행은 `run_in_background: true`를 사용하고, 종료 후 출력에서 `runs.json` 경로를 확인한다.

## 3. 채점과 채점자 간 일치도 확인

실행 결과 디렉터리 하나당 `Agent(subagent_type="eval-grader")` 하나를 배정하고 병렬 실행한다.
같은 `runs.json`은 한 채점자가 모든 회차를 처리한다. 프롬프트에는 결과 디렉터리, 회차 수,
케이스 디렉터리를 전달한다.

집계기는 필수 채점값 누락이나 하네스 실행 오류가 있으면 종료 코드 1로 중단한다.
미채점 회차는 채점을 완료하고, 하네스 오류가 난 회차는 다시 실행한다.
`detected`의 `null`은 미검출을 뜻하므로 유효하다. 선행 결함이 없는 케이스는 모든 회차의
`drift_isolated`를 `null`로 둔다. 러너가 기록한 `immediate_fail`은 덮어쓰지 않는다.

첫 평가에서는 사용자 또는 주 에이전트가 회차 하나를 별도로 채점해 `runs.human.json`으로 저장한다.

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/eval/agent-eval/scripts/calibrate.py <run-dir>/runs.json <run-dir>/runs.human.json
```

채점자 간 일치율이 85% 미만이면 자동 채점 결과로 결론을 내리지 않는다.
불일치한 항목의 정답지와 루브릭을 검토·수정한 뒤 다시 채점한다.

## 4. 보고서 작성

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/eval/agent-eval/scripts/report.py <BEFORE runs.json...> <AFTER runs.json...> \
  --cases-root ~/.claude/evals/cases/<repo> --out <run-root>/report.md
```

집계기가 생성한 총점·난이도별 검출률·평가 항목별 점수·비용·판정에 다음 해석을 추가한다.

- **차이의 근거:** 각 설정의 행동과 누락을 실제 보고 내용으로 설명한다.
- **난이도별 한계:** 자동 검출 가능한 T1 성과와 규칙·도메인 판단이 필요한 T2·T3 성과를 구분한다.
- **즉시 FAIL:** 정답지 열람 등 신뢰 위반이 있으면 보고서 맨 위에 명시한다.
- **다음 조치:** 프롬프트 수정, 반복 발견에 대한 규칙 보완, 추가할 평가 케이스를 제안한다.

채택 기준은 `rubrics/agent-run-quality.md`의 3절을 따르며 `report.py`가 계산한다.
비용 증가는 총점과 별도로 보고한다. 사용자에게 보고서 경로와 판정을 전달한다.
공유용 페이지를 요청받으면 실행 환경에서 지원하는 게시 방법을 사용한다.

## 결과 해석 시 주의사항

- `run-case.sh`는 원본 저장소의 자동 메모리를 실행 전후로 백업·복원한다. `memory-written/`가
  생성됐으면 평가 중 메모리에 저장하려던 내용을 보고서에 명시한다.
- `--harness`는 `agent-memory/`를 기본 제외한다. 메모리를 포함하면 이전 실행의 학습 효과가
  설정 변경의 효과와 섞일 수 있다.
- `k=1` 결과로 신뢰성을 판단하지 않는다. 심각도 일관성은 같은 결함을 두 회차 이상 검출했을 때
  측정할 수 있다. 케이스가 하나면 결론을 해당 케이스로 한정한다.
- 높은 통과율만으로 케이스가 너무 쉽다고 단정하지 않는다. 난이도별 검출률과 실제 실패 사례를
  함께 검토하고, 기존 회귀 케이스를 유지하면서 부족한 유형을 추가한다.
