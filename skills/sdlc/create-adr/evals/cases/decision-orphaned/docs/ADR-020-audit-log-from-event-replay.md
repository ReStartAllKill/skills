# ADR-020 — 감사 로그는 이벤트 스트림 재생으로 세운다

## 결정

워크스페이스의 감사 로그는 별도 저장소에 쌓지 않고, 필요할 때마다 이벤트 스트림을 처음부터 재생해 만든다. 감사 로그는 어느 시점에도 스트림의 함수이고, 스트림과 감사 로그가 어긋나는 상태는 정의상 생기지 않는다.

### Non-goals

- 감사 항목의 분류 체계는 여기서 정하지 않는다. 분류는 보안 규정이 정본이다.
- 외부 감사 시스템으로 내보내는 형식은 이 결정에 들어오지 않는다.

## 문맥과 결정 요인

감사 로그를 데이터베이스에 따로 쌓으면 스트림과 두 벌이 되고, 두 벌은 언젠가 갈라진다. 갈라진 뒤에는 어느 쪽이 맞는지 사람이 판정해야 하는데, 감사 기록에서 그 판정은 비싸다.

**결정 요인** — 아래 대안의 공통 축이다.

- **정본의 단일성:** 같은 사실이 두 곳에 있으면 갈라진다. 갈라지지 않는 유일한 방법은 한 곳만 두는 것이다.
- **재구성 시간:** 감사 로그를 세우는 데 걸리는 시간이 마감 처리의 하한이다.
- **외부 의존:** 이벤트 보관소가 서면 감사 로그가 함께 선다.

### ASM-001 — 보관소가 최초 구간까지의 이벤트를 계속 보관한다

지금 쓰는 보관소가 전 구간 이벤트를 준다는 것을 확인했을 뿐, 보관 기간에 대한 계약상의 약정은 없다. 재생이라는 방식 전체가 이 전제 위에 서 있다.

## 대안

### ALT-001 — 이벤트 재생 (채택)

감사 로그가 스트림의 함수라 두 벌이 갈라질 자리가 없다. 재구성 시간이 이벤트 수에 비례해 늘고, 이벤트를 주는 쪽에 종속된다.

### ALT-002 — 집계기가 쓰는 감사 테이블

읽기가 상수 시간이고 보관소가 멈춰도 감사 로그가 선다. 스트림과 테이블이 두 벌이 되어 정합을 따로 지켜야 한다.

**채택 근거:** 감사 기록에서 두 벌이 갈라지는 사고의 수습 비용이 재구성 시간보다 크다고 봤다.

## 결과

- 얻는 것: 감사 로그와 스트림이 어긋나는 상태가 생기지 않는다.
- 감수하는 제약: 감사 로그를 읽을 때마다 이벤트를 재생하므로 마감 처리 시간이 이벤트 수를 따라 늘어난다.
- 감수하는 제약: 이벤트 보관소 제공자에 종속된다. 제공자를 바꾸려면 이벤트 전 구간을 다시 받아야 한다.
