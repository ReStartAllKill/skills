# 결정 기록 작성

여기 적을 것은 6개월 뒤 «왜 이렇게 했지» 를 묻는 사람이 필요로 하는 것뿐이다. 그 사람은 이
대화도 그 스펙 폴더도 못 본다.

## 절차

시작·검사·승인은 `<sdlc_runtime>/conventions.md` 의 「스킬 공통 절차」를 따른다.
결정 기록의 계약은 `references/adr.md` 를 읽는다 — 절·ID·상태·핀이 거기 있다.

프로필에 `adr_dir` 이 없으면 이 레포는 ADR 을 안 쓴다. 지어내지 말고 어디에 둘지 묻거나
`/sdlc-init` 으로 보낸다. `adr_repo` 가 있으면 결정은 그 레포에 산다.

### 1. ADR 인지 판정한다

`references/adr.md` §판정 이 정본이다. 걸리지 않으면 **여기서 멈추고** plan 의 `TD-*` 나
PR 본문으로 보낸다.

**결정이 아직 안 났어도 연다.** `draft` 로 두고 대안까지 채운다. 채택안은 승인 때 표기한다.

### 2. 선례와 번호를 본다

```sh
node <sdlc_runtime>/tools/adr-index.mjs <레포 루트> --next
```

다음 번호와 기존 ADR 목록이 나온다. 진행 중인 브랜치가 같은 번호를 쥐고 있는지
`git log origin/main..` 로도 본다.

**기존 ADR 이 이미 그 결정을 담고 있으면 새로 만들지 않는다.** 결론을 바꾸는 것이면 그 ADR 을
`superseded` 로 옮기고 후속을 쓴다 — **승인된 ADR 의 본문을 고쳐 결론을 바꾸지 않는다.** 감사
추적이 거기서 끊긴다.

### 3. 정본 위치를 가른다

쓰기 전에 딸린 정보가 각각 어디 살지 정한다 — `references/adr.md` 의 정본 표를 따른다.
이걸 건너뛰면 ADR 이 스펙을 삼킨다.

### 4. 쓴다

`assets/adr-template.md` 로 작성하고 `<adr_dir>/ADR-{NNN}-{kebab-slug}.md` 에 둔다.

- **`scope` 를 채운다.** 이 결정이 제약하는 코드 경로다. 비우면 `task-brief` 가 이 ADR 을
  구현 에이전트에게 싣지 못하고, `confirms` 드리프트 검사도 돌지 않는다 — **비운 ADR 은 장식이다.**
- **`confirms` 를 채운다.** 지켜졌는지 판정하는 테스트 이름이나 게이트 명령. 검사기가 `scope`
  안에서 그 이름을 찾는다. 식이나 fixture 를 옮겨 적지 말고 어느 테스트가 정본인지를 가리킨다.
- **하나의 ADR 에 하나의 결정.** 독립적으로 뒤집힐 수 있는 선택이 딸려 오면 나눈다. 채택안을
  설명하는 데 필요한 명칭 변경 정도는 결정 절에 한 줄로 포함한다.
- **결과 절에 감수하는 제약을 반드시 적는다.** 없으면 검사기가 반려한다. 대가 없는 결정은
  결정이 아니라 사후 정당화다.
- **전제(`ASM-*`)를 적었으면 `RV-*` 로 짝짓는다.** 전제만 있고 재검토 조건이 없으면 전제가
  틀렸을 때 아무도 깨우지 않는다. `RV-*` 는 시한이 아니라 참·거짓이 판정되는 조건으로 쓴다.

사람만 답할 수 있는 것(규제 해석 · 운영 정책 · 파트너 합의 · 우선순위)은 묻는다. 지어내지 않는다.

### 5. 검사하고 승인한다

```sh
node <sdlc_runtime>/tools/check-artifacts.mjs <ADR 경로>
node <sdlc_runtime>/tools/lint-prose.mjs     <ADR 경로>
node <sdlc_runtime>/tools/adr-index.mjs      <레포 루트>
```

공통 절차대로 `in_review` 로 저장해 보고하고 **바로 승인 편집을 시도한다.** 가드가 그 편집을
승인 다이얼로그로 보내므로 그 다이얼로그가 곧 승인 질문이다. 승인 뒤 인덱스를 다시 만들고
ADR 과 인덱스를 함께 커밋한다.

## 문체

**독자는 6개월 뒤 «왜 이렇게 했지» 를 묻는 사람이다.** 세션에도 논의 스레드에도 접근할 수 없다.

- **한 줄 검사**: 문장마다 «이 결정을 모르는 사람에게 새 정보를 주는가» 를 묻고, 아니면 지운다.
  이 검사가 작업 경위 · 판단 과정 서술 · 구현 상세를 전부 걸러낸다.
- **보수적으로 쓴다.** 주장의 강도를 근거의 강도에 맞춘다. 검토가 안 끝난 법률 · 회계 · 규제
  판단은 «~된다» 가 아니라 «~를 전제로 한다» 이고 `ASM-*` 에 남긴다. 수치 · 기한 · 성능 주장은
  출처가 있을 때만 쓰고, 없으면 조건으로 바꾼다. 「반드시 · 절대 · 불가능」은 구조적으로 그럴
  때만 — 운영 규칙으로 막는 것은 «금지한다» 이지 «불가능하다» 가 아니다.
- **채택안을 띄우려고 기각안의 단점을 부풀리지 않는다.**
- 나머지 문체 규칙은 `references/prose.md` 가 정본이다.

핀할 것을 안내한다.
