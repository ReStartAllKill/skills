# 스펙 수정

기존 사슬에 피드백을 반영한다. 변경에 필요한 부분만 조사하고 수정한다.

## 1. 영향 확인

1. `.claude/spec-profile.yml`과 사슬의 intent·spec·plan을 읽는다. `from_finding`이 있으면
   해당 finding도 읽는다. 런타임을 찾는 순서는 `references/runtime.md`가 정본이다.
2. 런타임의 `conventions.md`, `references/schema.md`를 읽는다. 작업 수정에는
   `references/tasks.md`, 문장 수정에는 `references/prose.md`를 추가로 읽는다.
3. 체크박스·실행 기록과 `plan-progress.mjs` 결과를 대조해 완료된 작업을 확인한다.

| 변경 내용 | 수정 대상 | 후속 갱신 |
|---|---|---|
| 목적·제약 | intent | 관련 OUT/CON을 참조하는 spec·plan |
| 외부 동작 | spec | 관련 FR/NFR을 구현하는 작업 |
| 구현 방법 | plan의 설계 결정 | 관련 작업 |
| 작업 분할·순서 | plan의 작업 | 의존 관계와 레벨 |

의미가 바뀐 문서와 영향받은 하위 문서는 `in_review`로 되돌린다. 티어가 커졌다면 intent부터 바꾼다.
오탈자 수정은 상태를 유지한다. 상위를 커밋한 뒤 하위의 버전 핀을 갱신한다.

**이미 실행 중인 plan 은 재승인 뒤 `in_progress` 로 되돌린다.** `in_review` → `accepted` 로 끝내면
그 계획서는 실행 중인데 «아직 시작 안 한» 상태로 남는다. 그러면 `guard-approval.sh` 가 남은 작업의
체크박스 갱신마다 «승인된 문서의 상태 유지 변경» 으로 승인을 묻고, `claude -p` 자율 경로에서는 아예
거부한다 — 일은 되는데 계획서에 안 찍히고, 아무도 그 어긋남을 안 본다.
체크된 작업이 하나라도 있으면 실행 중이다 — `plan-progress.mjs` 가 이 어긋남을 오류로 낸다.

## 2. 변경안

이미 확인한 근거는 다시 조사하지 않는다. 추가 조사가 필요하면 프로필의 `pattern_agent`나
읽기 도구를 사용한다. 구현·감사 에이전트는 실행하지 않는다.

바뀔 요구사항·작업·릴리스 영향과 기존 완료 작업에 미치는 영향을 구체적으로 보여준다.
사용자가 요청한 반영 범위는 진행하고, 미결정된 제품 판단이나 범위 확대가 있을 때만 확인한다.

## 3. 반영과 검사

1. 해당 항목만 수정한다. 완료된 작업은 지우거나 다른 뜻으로 바꾸지 않는다.
   되돌리기나 추가 변경은 새 작업으로 기록한다. 삭제한 ID는 재사용하지 않는다.
2. §실행 기록의 변경 기록에 변경 이유와 영향 ID를 남긴다.
3. `check-artifacts.mjs <스펙 폴더>`와 `lint-prose.mjs <스펙 폴더>`를 실행한다.
   버전 핀, Must 요구사항의 작업 연결, 같은 레벨의 파일 충돌을 확인한다.
4. 오류를 해결한 뒤 공통 절차에 따라 필요한 재승인을 처리한다. plan 이 실행 중이었으면 재승인
   직후 `status` 를 `in_progress` 로 되돌리고 같은 커밋에 싣는다.
5. `plan-progress.mjs <스펙 폴더>` 를 마지막으로 한 번 더 돌려 어긋남이 0 인지 본다 — 특히
   «체크된 작업이 있는데 status 가 …» 오류가 없어야 한다.

## 보고

문서 경로, 변경 요약, 상태, 검사기·린터의 오류와 경고 수, 재검증이 필요한 작업을 보고한다.
구현을 이어갈 수 있으면 `/implement-spec <경로>`를 안내한다.
