# 실행 방식의 근거

## 격리와 병합

Git은 같은 브랜치를 여러 워크트리에 체크아웃할 수 없으므로 작업마다 브랜치를 만든다.
분기 기준은 현재 `target_branch`다. 앞 레벨의 결과를 커밋하고 병합해야 다음 레벨이 이를 포함한다.

빌드 산출물을 공유하는 검증은 동시에 실행하지 않는다. `worktree_dir`는 Git·린터·포맷터의
검사 대상에서 제외해 중복 검사를 막는다. 이미 워크트리를 만들었으므로 Agent의 `isolation`은 추가하지 않는다.

브랜치는 하나씩 병합해 충돌한 작업을 식별한다. 충돌이 나면 범위 밖 편집, 의존 관계,
외부 브랜치 변경을 조사한다. 파일 선언 오류만이 원인이라고 단정하지 않는다.

## 증거와 판단

커밋 귀속과 검증 기록의 계약은 런타임의 `references/tasks.md`를 따른다.
체크박스는 수용 기준 충족 판정이고 실행 기록은 계획과 실제의 차이이므로 훅이 자동 작성하지 않는다.

테스트 이름이 AC와 같아도 테스트 내용이 올바르다는 뜻은 아니다. 코드·테스트를 AC별로 대조하고,
프로필에 독립 감사 역할이 있으면 구현과 다른 에이전트가 검토한다.

중간 레벨이 작업 범위 검증만 도는 이유는 증거의 정의에 있다. `plan-progress`가 보는 것은 모든 작업을
덮는 최신 전체 검증 로그 하나뿐이므로, 레벨마다 돌던 전체 검증은 그 로그가 되지 못한 채 회귀를 조금
일찍 발견하는 값만 샀고 값으로 스위트 전체를 레벨 수만큼 다시 도는 시간을 냈다. 대신 scoped 로그를
증거로 인정하는 길은 버렸다 — 라벨이 붙은 로그는 자기가 이름 댄 작업을 스위트의 일부에 대해서만
통과시킨 것이고, 그것을 전체 통과로 읽는 것이 바로 `plan-progress`가 거부하는 주장이다.
감사를 티어로 가르는 이유도 같다. `light`는 되돌릴 수 있고 외부 계약을 건드리지 않는 변경이라
워크트리 하나와 테스트 하나가 이미 덮으며, 모든 변경에 붙는 감사는 늘 걸리는 검사와 마찬가지로
읽히지 않게 된다.

## 승인 범위

로컬 작업 커밋과 병합은 구현 절차에 포함된다. push와 PR은 사용자의 명시적 요청 범위를 따른다.
승인된 외부 동작과 코드 제약이 충돌하면 근거를 보고하고 `/iterate-spec`으로 계약을 갱신한다.
