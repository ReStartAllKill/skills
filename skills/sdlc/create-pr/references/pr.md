# PR 본문

PR 본문의 목적은 **변경의 이유(why)와 리뷰어가 집중할 지점을 전달하는 것**이다. 무엇이 바뀌었는지(what)는
diff 와 GitHub Files 탭이 이미 보여준다 — 본문에서 파일을 그대로 풀어쓰지 않는다. 대신 리뷰어가 _왜_ 이
변경이 필요했고, _어디를_ 주의 깊게 봐야 하는지를 짚는다. 잘 쓴 PR 은 사람이 쓴 리뷰 가이드처럼 읽힌다.

분량은 변경 규모에 맞춘다. 한 줄 수정에 표와 섹션을 가득 채우면 신호보다 잡음이 많아진다.

## 산출물 세트가 있으면 «왜»는 이미 승인돼 있다

브랜치가 `<spec_dir>`의 산출물을 변경했으면 Problem과 Intent를 diff에서 다시 세우지 않는다.
승인된 문서에서 가져오고 **그 ID 를 적는다.** 본문과 문서가 갈리면 어느 쪽이 계약인지 아무도 답하지
못하고, 리뷰어는 이미 합의된 판단을 처음부터 다시 하게 된다.

| 본문 섹션 | 산출물 세트에서 가져오는 곳 | 산출물 세트가 없으면 |
|---|---|---|
| 🎯 Intent | `intent.md` §목표 결과 `OUT-*` | 커밋과 diff 에서 목표 상태를 세운다 |
| 🔍 Problem | `finding.md` §관측 `EV-*` · `intent.md` §문제 | 이슈·알림·요청에서 세운다 |
| 🔄 Behavior & Changes | `spec.md` §시나리오 `SCN-*` · §요구사항 `FR-*` | 관측되는 동작을 직접 정리한다 |
| ⚠️ Risks & Review Points | `plan.md` §위험 `RISK-*` + 프로필 `pr_review_focus` | `pr_review_focus` 와 아래 축 목록만 |
| 🧪 Verification | `plan.md` §실행 이력의 완료 증거 · `AC-*` | 실행한 검증 명령과 결과 |

- **복제가 아니라 인용이다.** 요구사항 원문을 옮겨 붙이지 않는다 — 리뷰어가 문서를 열 수 있게 ID 와
  상대 경로만 남긴다 (`근거: OUT-002`, `.sdlc/specs/2026-09-08-cancel/spec.md`).
- **머지 뒤에는 코드와 PR 본문이 정본이다**(`conventions.md` §Authority and lifetime). 그래서 산출물 세트를 인용하는
  일은 이 PR 이 열려 있는 동안의 다리이지, 문서를 코드에서 참조하라는 뜻이 아니다.
- 산출물 체계를 사용하지 않는 레포에서는 이 표의 오른쪽 칸만 따른다. 없는 문서를 지어내지 않는다.
- **spec 이 부르지 않은 동작을 숨기지 않는다.** `pr-context.sh` 의 `unplanned-files:` 는 어느 작업의
  `files` 에도 없는 변경 파일이다 — 작업 커밋은 자기 `files` 안에 갇히지만, 그 밖에서 한 수정이 곧 «spec 에
  없는 동작» 이 들어오는 자리다. 파일마다 셋 중 하나로 닫는다: 승인된 요구사항의 몫이면 plan 이 낡은 것이라
  `/iterate-spec` 으로 작업을 더하고, 이번 변경과 무관하면 커밋을 갈라 PR 에서 뺀다, 둘 다 아니면
  `### Changes` 에 **`(spec 밖)`** 을 달아 적고 밖에서 관측되는 동작이면 PR 전에 spec 에 먼저 더한다.
  판정 없이 넘어간 «spec 밖» 은 리뷰어가 diff 에서 찾아내야 하고, 그러면 본문이 리뷰 가이드가 아니다.

## 섹션

본문 구조는 레포에 `.github/pull_request_template.md` 가 있으면 **그것을 그대로 따른다.** 없으면 아래
다섯 섹션을 순서대로 쓴다.

**최소형은 Intent + Problem 둘뿐이다.** deps bump·CI 한 줄·오타 수정은 여기서 끝낸다. 해당 없는
섹션은 "없음" 이라고 쓰지 말고 섹션째 지운다 — 표 골격이 있으면 채우고 싶어지지만 빈 행·"변경 없음"
행은 신호를 묻는 잡음이다.

| 섹션 | 언제 남기나 | 형식 |
|---|---|---|
| 🎯 Intent | 항상 | 산문 + `### Non-goals` 불릿 |
| 🔍 Problem | 항상 | 산문 + 원인 콜아웃 |
| 🔄 Behavior & Changes | 관측되는 동작이 바뀌거나 변경이 여러 갈래일 때 | 표 + `### Changes` 불릿 |
| ⚠️ Risks & Review Points | 위험·확인 지점이 있을 때 | 표 + Reviewer Focus 콜아웃 |
| 🧪 Verification | 검증할 동작·지표가 있을 때 | 지표 표 + 근거 한 문단 + 불릿 |

### 🎯 Intent (항상)

**이 PR 이 끝난 뒤 시스템이 어떤 상태이길 바라는가** 를 한두 문장으로. 구현 방법이 아니라 목표 상태다 —
"취소 API 를 추가한다" 가 아니라 "신청자가 실행 전에 스스로 취소할 수 있게 한다".

`### Non-goals` 에는 **이번에 하지 않는 것** 을 불릿으로 적어 스코프 논쟁을 미리 닫는다. 없으면 하위
제목째 지운다.

### 🔍 Problem (항상)

**지금 무엇이 불편·위험·부정확한가.** 어떤 문제·요구·스펙이 이 변경을 부르는지 — diff 가 못 보여주는
유일한 정보라, 여기가 비면 본문 전체가 무의미해진다.

Intent 와 짝이다. **Problem 은 출발점, Intent 는 도착점.** 두 섹션이 같은 문장의 앞뒤를 뒤집은 꼴이면
Problem 이 현재 상태를 안 쓴 것이다.

**작성자가 아니라 시스템을 쓴다.** «정리하고 싶었다»·«전부터 걸렸다» 는 문제가 아니라 동기다. 무엇이
얼마나 나쁜지를 관측으로 쓴다 — 산출물 체계가 있으면 `finding.md` 의 `EV-*` 가 이미 그 모양이다.

**수치는 결론을 세우는 것만 남긴다.** 관측 분포·건수 나열은 Verification 표로 보내고, 여기에는 "얼마나
나쁜가" 를 한 번에 보여주는 값 두어 개만 둔다.

원인 규명이 쟁점이면 콜아웃으로 원인과 배제한 후보를 갈라 둔다 — 리뷰어가 같은 의심을 되풀이하지 않게 한다.

```markdown
> **Root cause:** 요청마다 발생하는 password login 왕복
>
> **Not the cause:** 목록 API 의 전체 조회
```

근거 링크는 이 섹션 끝에. 이슈는 동사로 해결 정도를 구분한다 — 완전히 닫으면 `Closes #N`, 부분·참조면
`Refs #N`, 선행 PR 이 먼저 머지돼야 하면 `Depends on #N`. 산출물 문서와 ADR 은 상대 경로와 ID 로 건다.

### 🔄 Behavior & Changes (동작이 바뀌거나 변경이 여러 갈래일 때)

표는 **밖에서 관측되는 것** 만 쓴다 — API 응답, 상태 전이, 배치 스케줄, 온체인 기록.

```markdown
| Scenario         | Before | After |
| ---------------- | ------ | ----- |
| `PENDING` 취소   | 거부   | 허용  |
| `DISBURSED` 취소 | 거부   | 거부  |
| 중복 취소        | -      | 멱등  |
```

- **칸은 낱말로** 쓴다(`허용`·`거부`·`멱등`·`-`). ✅/❌ 는 쓰지 않는다 — "의도대로 거부" 가 결함으로
  오독된다. 검증 결과는 이 표가 아니라 Verification 이 맡는다.
- 시나리오는 **정상·실패·경계값·권한·기존 동작 유지** 축으로 훑어 빠진 게 없는지 본다. spec 이 있으면
  `SCN-*` 와 `EDGE-*` 가 이미 그 축이다.
- 관측되는 동작이 그대로인 내부 리팩터면 표는 지우고 `### Changes` 만 남긴다.

`### Changes` 는 **무엇을 그렇게 정했는지가 먼저** 고, 구현 세부는 필요한 만큼만 하위 불릿으로 내린다.
파일 나열이 아니다 — 그건 Files 탭에 있다. plan 의 `TD-*` 가 있으면 그 결정이 여기 온다. spec 이 부르지
않은 변경은 `(spec 밖)` 을 달아 따로 선다 — 어느 요구사항의 몫도 아니라는 것이 리뷰어가 알아야 할 정보다.

```markdown
- `TokenProvider` 신설 (TD-002)
  - JWT `exp` 를 기준으로 30초 여유를 두고 access 만료 판단
  - `ROTATE_REFRESH_TOKENS` 에 따라 갱신 응답의 새 refresh token 을 유지
- 401 재시도 추가
- 만료 로그의 시각을 UTC 로 통일 (spec 밖)
```

### ⚠️ Risks & Review Points (위험·확인 지점이 있을 때)

```markdown
Risk 는 확률이 아니라 **틀렸을 때 치르는 대가** — 🔴 조용히 잘못된 상태로 남음 · 🟡 드러나고 되돌릴 수 있음 · 🟢 영향 범위가 좁음.

| Area           | Risk      | Review Point                       |
| -------------- | --------- | ---------------------------------- |
| Business Logic | 🔴 High   | 잘못된 상태 전이가 발생하지 않는가 |
| Authorization  | 🟡 Medium | 신청자 본인만 취소 가능한가        |
| Concurrency    | 🟡 Medium | 중복 요청에 안전한가               |

> **Reviewer Focus:** `DISBURSED → CANCELLED` 전이는 어떤 경로에서도 발생하면 안 된다. 상태 전이 표는 `loan-state.ts` 한 곳에서만 정의된다.
```

**표 위 한 줄은 그대로 둔다** — 이 표를 처음 보는 리뷰어에게 Risk 열이 확률이 아니라 대가의 등급임을
알려주는 범례다. 이 줄이 없으면 🔴 가 "일어날 확률이 높음" 으로 읽혀 섹션의 뜻이 뒤집힌다.

`Risk` 는 확률이 아니라 **틀렸을 때 치르는 대가** 로 매긴다. 확률은 작성자가 낙관하기 쉽고, 리뷰어가
알고 싶은 건 "어디부터 볼까" 이기 때문이다.

| 등급 | 뜻 |
|---|---|
| 🔴 High | 틀리면 데이터·자금·권한이 잘못되거나, **조용히** 잘못된 상태로 남는다 |
| 🟡 Medium | 틀리면 기능이 실패하지만 드러나고 되돌릴 수 있다 |
| 🟢 Low | 틀려도 영향 범위가 좁고 국지적이다 |

즉시 터지는 오류보다 **알아채지 못하는 오류** 가 위다 — 사후 정정 비용이 큰 축(온체인 기록·집계값)이
여기 해당한다.

- **Review Point 는 사람만 판단할 수 있는 것.** typecheck·lint·CI 가 잡는 건 적지 않는다. plan 의
  `RISK-*` 와 intent 의 `CON-*`(제약·불변 조건)이 1순위 후보다. 산출물 체계가 없으면 마이그레이션 안전성·권한·
  동시성·에러 처리 순으로 본다.
- **바뀌지 않은 영역은 행을 만들지 않는다.** `| Database | 🟢 Low | Schema 변경 없음 |` 같은 행은 정보가
  아니라 잡음이다.
- **Reviewer Focus 는 확인해야 할 사실을 단언으로** 쓰고, 볼 위치를 한 곳 지목한다. 콜아웃은 하나만.
  머지 순서·선행 PR 같은 주의점도 여기 싣는다.
- **저자가 답을 구하는 질문은 콜아웃에 섞지 않는다.** 설명과 질문이 한 덩어리면 리뷰어가 무엇을
  확인하고 무엇에 답해야 하는지 갈리지 않는다. 질문은 `**Open question:**` 줄로 따로 뺀다.
- **🟢 만 남으면 섹션째 지운다.** 국지적 영향만 있는 표는 리뷰 순서를 못 정해주므로 자리값을 못 한다.
  위험이 정말 없으면 억지로 만들지 않는다.

**다음을 건드리면 이 섹션을 생략할 수 없다** — 최소형(Intent + Problem)으로 끝내지 못한다.

- PII·자격증명·secret 처리
- 되돌리기 어려운 쓰기 경로(결제·온체인·외부 전송)
- DB 스키마·마이그레이션
- 권한 경계(authz)

판정 기준은 프로필의 `pr_review_focus` 와 같고, **`pr-body-lint.sh` 가 이 조건을 직접 강제한다** —
변경 파일과 프로필 규칙을 대조해, 축이 걸렸는데 Risks 섹션이 없으면 exit 1 이다.

다만 규칙은 **파일 경로만** 본다. 경로에 드러나지 않는 위험(평범한 이름의 파일이 PII 를 로그로 흘리는
등)은 걸러지지 않으므로 위 목록을 직접 훑는 판단이 여전히 필요하다. 프로필이 없거나 Git 저장소 밖이면
이 검사는 돌지 않는다.

### 🧪 Verification (검증할 동작·지표가 있을 때)

**지표를 표로 먼저** 보이고, 그 값이 어디서 나왔는지를 아래 한 문단으로 받는다. 마지막에 확인한 항목을
불릿으로 짧게 붙인다.

```markdown
| Metric                  |     Before | Expected After |
| ----------------------- | ---------: | -------------: |
| `/investments/{id}` p50 |    1,748ms |         ~566ms |
| Password login          | ~3,100/day |     ~1/process |

상류 실측값(로그인 566ms / 조회 283ms / refresh 50ms)을 기준으로 계산했으며, 기존 관측 p50(1,748ms)과 모델값(1,698ms)이 근접한다.

- Unit tests: 인증 lifecycle / concurrency / 401 retry 검증 완료 (AC-004 · AC-007)
- OpenAPI snapshot: 변경 없음
```

- **측정값과 예측값을 섞지 않는다.** 실측은 근거 문단에, 예측은 `Expected After` 열에 둔다.
- 불릿은 **무엇을 덮었는지** 를 적는다. 통과 여부만 적으면 CI 가 이미 말한 것이라 새 정보가 없다.
  plan 의 실행 이력과 `AC-*` 가 그 재료다.
- 지표가 없는 변경(문서 수정 등)이면 섹션째 지운다.

## 문체·분량

**독자는 diff 와 코드만 가진 리뷰어다.** 세션·산출물 문서·논의 스레드 어디에도 접근할 수 없다고 보고
쓰되, 산출물 문서는 ID 와 경로로 열 수 있게 남긴다.

- **한 줄 검사**: 문장마다 "diff 를 안 본 리뷰어에게 새 정보를 주는가" 를 묻고, 아니면 지운다. 이 검사
  하나가 작업 경위·Phase 언급·판단 과정 서술·파일 나열을 전부 걸러낸다.
- **분량 상한**: Intent 는 한두 문장, 표 하나는 6행 이내, 본문 전체 70행 이내. 넘으면 문장을 다듬기
  전에 **섹션·행을 지울 게 없는지** 먼저 본다.
- **메타정보 금지**: `file.ts:99` 류 위치 참조는 리뷰어가 실제로 열어봐야 할 한두 곳만 남긴다.
  "N건 중 N건", "그중 2건은 …" 같은 부수 관찰, 내부 상수 나열, 작업하며 알게 된 경위는 전부 뺀다 —
  결론을 바꾸지 않는 숫자는 정보가 아니라 부담이다.
- **번역체 금지**: `~에 대한`, `~를 통해`, `~에 의해`, `~되어진`, `~할 수 있도록 지원` 같은 영어 번역투를
  쓰지 않는다. 목록은 `prose.md` 와 같은 축이다. 주어를 세우고 능동으로 쓰면 대개 짧아진다.
- **줄바꿈**: 문단당 한 줄로 쓴다. 소스코드식 ~100자 하드랩 금지 — GitHub 는 단일 개행을 그대로
  렌더링해 어색하게 꺾인다.
- 문체는 **체언·간결 종결**(`~함`, `~추가`, `~수정`, `~제거`). 합쇼체(`~했습니다`·`~합니다`) 금지.
- 도메인 용어를 쓴다. 은유 조어를 만들지 말고, 코드 심볼은 정확성이 필요한 곳에만 백틱으로 쓴다.

## 언어

**PR 본문의 언어는 프로필의 `lang` 이 정한다**(기본 `ko`). 대화 언어를 따르지 않는다 — 본문은
리뷰어가 읽고 레포에 남는 글이라 산출물과 같은 자리다(`<adr_dir>` 의 ADR-001). 골격도 그 언어판
(`assets/<lang>/pr-body-template.md`)을 쓴다.

`pr-body-lint.sh` 의 문체 검사는 낱말 목록이라 `lang` 으로 갈린다. `ko` 는 합쇼체·번역체를, `en` 은
수동태·에두른 표현을 본다. 합쇼체에 해당하는 검사는 `en` 에 **없다** — 영어에 대응하는 화계가 없어서지
건너뛰는 것이 아니고, 어느 검사가 그런지는 스크립트 머리의 표가 말한다.

`lang` 과 본문의 언어가 다르면 문체 검사가 하나도 안 걸리는데, 안 걸리는 것은 통과와 구분되지 않는다.
그래서 린터가 `lang-unsupported` 를 찍는다. 막지는 않는다 — 런타임 `prose.md` §언어와 같은 자리다.

**아래 예시는 한국어다.** 이 참조 문서 자체가 한국어라 그렇고, 보여주는 것은 낱말이 아니라 **어느
섹션을 남기고 어느 섹션을 지우는가** 다. `lang: en` 이면 같은 골격을 영어로 쓴다.

## 예시

### 최소형 — deps bump

```markdown
## 🎯 Intent

`fastify` 를 5.2 로 올려 보안 패치를 받는다.

## 🔍 Problem

5.1.x 는 `Content-Type` 파싱에 DoS 취약점(GHSA-xxxx)이 있고, 우리 라우트는 전부 body 파서를 거친다. 상위 릴리스 노트에 동작 변경은 없다.

Refs #412
```

### 전체형 — 동작이 바뀌는 변경

```markdown
## 🎯 Intent

신청자가 집행 전 대출 신청을 스스로 취소할 수 있게 한다 (`근거: OUT-002`).

### Non-goals

- 집행 후 중도상환. 별도 산출물 체계로 뺀다.

## 🔍 Problem

지금은 취소 창구가 CS 뿐이라 취소 1건에 평균 2.3영업일이 든다. 그동안 신청은 심사 큐에 남아 심사 인력이 이미 취소된 건을 처리한다.

`.sdlc/specs/2026-09-08-cancel-application/spec.md` · SCN-001 · FR-003

## 🔄 Behavior & Changes

| Scenario         | Before | After |
| ---------------- | ------ | ----- |
| `PENDING` 취소   | 거부   | 허용  |
| `DISBURSED` 취소 | 거부   | 거부  |
| 중복 취소        | -      | 멱등  |

### Changes

- 상태 전이를 `loan-state.ts` 한 곳으로 모음 (TD-002)
  - 전이표에 없는 조합은 예외로 떨어뜨려 조용한 통과를 막음
- 취소 API 는 신청자 본인 토큰만 받음

## ⚠️ Risks & Review Points

Risk 는 확률이 아니라 **틀렸을 때 치르는 대가** — 🔴 조용히 잘못된 상태로 남음 · 🟡 드러나고 되돌릴 수 있음 · 🟢 영향 범위가 좁음.

| Area           | Risk      | Review Point                       |
| -------------- | --------- | ---------------------------------- |
| Business Logic | 🔴 High   | 잘못된 상태 전이가 발생하지 않는가 |
| Authorization  | 🟡 Medium | 신청자 본인만 취소 가능한가        |

> **Reviewer Focus:** `DISBURSED → CANCELLED` 전이는 어떤 경로에서도 발생하면 안 된다 (RISK-001). 전이표는 `loan-state.ts` 한 곳에서만 정의된다.

## 🧪 Verification

- 상태 전이: 전이표의 12개 조합 전수 (AC-004)
- 동시성: 같은 신청에 취소 2건 동시 요청 시 1건만 반영 (AC-007)
- 권한: 타인 토큰으로 취소 시 403
```
